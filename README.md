# EasyCraft

אפליקציית ניהול לנגרייה: לקוחות, תכנון מטבחים בדו־ממד ובתלת־ממד, תמחור,
ניסור, מלאי ותהליך עבודה. עברית, RTL, מותאמת לנייד — ועובדת בלי אינטרנט.

**האפליקציה החיה:** https://lzmediaspirit-hue.github.io/EasyCraft/

הכול רץ בדפדפן. אין שרת, אין חשבון, ואין נתונים שעוזבים את המכשיר — נגר
בשטח בלי קליטה צריך שהאפליקציה תעבוד. המחיר הוא שהנתונים חיים במכשיר אחד,
ומכאן מסך הגיבוי.

עיקרון מנחה: **בכל מסך רואים רק את מה שצריך עכשיו** — פעולה ראשית אחת,
בלי תפריטים עמוסים.

## הרצה

```bash
npm install
npm run dev           # שרת פיתוח על 5173
npm run typecheck     # חייב לעבור לפני כל קומיט
npm run build         # בדיקת טיפוסים + בנייה לייצור
npm run build:single  # קובץ HTML בודד שאפשר לפתוח בכל מקום
npm test              # 81 חבילות בדיקה — דורש שרת פיתוח פעיל
```

`build:single` אורז את הכול — קוד, עיצוב ואייקונים — לקובץ אחד ללא תלויות
חיצוניות, מקודד ASCII כדי שהעברית תיקרא נכון גם בלי הכרזת קידוד.

## מה האפליקציה עושה

**לקוחות ופרויקטים.** רשימה במיון עברי, חיפוש, חיוג מהרשימה, ושכפול
פרויקט — דירות בבניין אחד חוזרות על עצמן.

**אשף פרויקט.** חדר ← פריסת קירות (קיר יחיד, כמה קירות, או חדר מורכב
בשרטוט חופשי) ← מה יש על הקיר ← מידות. חלונות, דלתות, שקעים, נקודות מים,
עמודים ונישות מסומנים בגרירה.

**הדמיה.** חזית דו־ממדית לכל קיר עם גרירה, הצמדה לשכן ולקצה, וסרגל שמודד
בין כל שני דברים — כולל פינות הקיר. תלת־ממד איזומטרי עם סיבוב החדר, עריכה
בגרירה, וטבעת כפתורים סביב הארגז הנבחר. מתג חזית/פנים מסיר את הדלתות
ומראה מדפים, ארגזי מגירה ומוטות תלייה.

**ספריית מוצרים.** ארגזי תקן לפי חדר, בנייה ועריכה של ארגזים משלך, פנים
הארון לפי תאים, פינה מתה, פסי לד, קושרות וזכוכית.

**תכנון אוטומטי.** מנוע שמנצל את כל הקירות ומחזיר שלוש הצעות — הטובה
לנוחות, לאחסון ולמחיר — כל אחת עם תמונה מאותו מנוע שמצייר את ההדמיה.

**תמחור וניסור.** פירוק לחלקים, פריסה על פלטות אמיתיות, ומחיר לפי גוון ×
ליבה. תכנת ונגר אינם רואים תמחור.

**מלאי לוחות.** טבלה עם מיון וסינון, פחתים עם מידות, הפחתה אוטומטית לפי
סימון חיתוך, ומחשבון.

**תהליך עבודה.** שלבים לכל ארגז, צוות, מצב עבודה עם צבעים, ולוח התקנות.

## מבנה

```
src/
  db/          מודל הנתונים ובסיס הנתונים המקומי (IndexedDB)
  catalog/     ספריית המוצרים, מידות התקן ומנוע איורי הארגזים
  materials/   ליבות, גוונים והמחיר שבהצטלבות שביניהם
  costing/     פירוק ארגזים לחלקים, ניסור וחישוב מחיר
  workflow/    שלבים, צוות, מצב ארגז ותפקידים
  features/    מסכים לפי תחום, כל תחום עם שכבת גישה משלו
  nav/         ניווט מבוסס מחסנית
  ui/          רכיבים משותפים ויחידות מידה
tests/         81 חבילות בדיקה — ראו tests/README.md
scripts/       בניית הקובץ הבודד, והמרת ספרייה לקוד
```

מסך אינו ניגש ל-IndexedDB ישירות אלא דרך `*Repo`, וקריאות חיות דרך
`useLiveQuery`. מיגרציות רק עולות — למשתמש יש נתונים אמיתיים במכשיר.

### מקור אמת יחיד

מה שמחושב בשני מקומות מתחיל להיות שני דברים שונים. הקבצים האלה קיימים
כדי שזה לא יקרה:

| קובץ | השאלה שהוא עונה עליה |
|---|---|
| `features/design/placement.ts` | איפה הארגז עומד בחדר — על קיר ובאי כאחד |
| `features/design/collision.ts` | האם מותר להניח אותו שם |
| `features/design/isoMath.ts` | מה נראה, ומה מצויר לפני מה |
| `catalog/standards.ts` | מידות התקן בנגרות, עם נימוק לכל מספר |
| `costing/nesting.ts` | כמה פלטות באמת צריך |

## המנועים

### ניסור
`costing/nesting.ts` פורס את החלקים בניסור גיליוטינה רקורסיבי: כל חלק
מונח בפינת מלבן פנוי, והמלבן מתפצל בחתך שרץ מקצה לקצה — ולכן כל פריסה
ניתנת לניסור במסור פנלים בהגדרה. הכרסום נגרע פעם אחת בכל קו חיתוך בפועל,
ולא סביב כל חלק, כי זה מה שהמסור עושה.

אין היוריסטיקה שמנצחת תמיד, ולכן המנוע מריץ סל קבוע של שילובים ושומר את
הטובה ביותר. הסל מסודר והשוויונות נשברים לפי אינדקס, ולכן התוצאה
דטרמיניסטית: אותם חלקים נותנים תמיד אותה פריסה.

לכל חלק כיוון סיבים משלו. חזית, צד ודופן זרה נשארות בכיוון הלוח; מדף,
תחתית, קושרת וגב חופשיים לסיבוב, כי אף אחד לא רואה אותם.

**הפריסה הזו היא גם מה שסופר את הפלטות בתמחור** — מסך החישוב ומסך הניסור
מציגים את אותו מספר. זה מחליף את "שטח חלקים חלקי שטח פלטה", שהייתה הערכה
ששיקרה בדיוק במקום שכואב: חלק אחד ארוך יכול לדרוש פלטה שלמה גם כששטח
הפרויקט קטן.

### פירוק לחלקים
`costing/boards.ts` מפרק ארגז לצדדים, תחתית ותקרה, מדפים, גב, דלתות,
חזיתות מגירה ודפנות זרות — ומכבד את ההפחתות האמיתיות: דופן זרה היא חלק
מהמעטפת ולכן הגוף מתכווץ בעוביה, הגב יושב בחריץ ולכן קטן מהגוף וחוזר
בעומק החריץ, והחזית קטנה מהפתח במרווח שסביבה.

### התלת־ממד
שלושה שלבים: `unitSolids` בונה מכל ארגז לוחות ממשיים; `orderSolids`
קובע סדר ציור; `solidFaces` מצייר מכל לוח את הפאות שפונות אל הצופה.

הסדר אינו מפתח מיון אלא שאלה בין זוגות: שני לוחות שמופרדים על ציר כלשהו
ביחס לכיוון המבט — התשובה ודאית, וממנה נבנה הסדר הכולל. כל מפתח יחיד —
פינה קרובה, מרכז, גובה — נכשל במקרה אחר.

**מבחן הקרן** הוא איך יודעים שזה נכון: לכל נקודה על המסך נשאל איזה לוח
הקרן פוגשת ראשון, והתשובה מושווית ללוח שנצבע שם. `buildScene` מחזירה גם
את הלוחות עצמם, בדיוק כדי שאפשר יהיה לשאול את זה על החדר האמיתי. ככה
נתפס שהסדר נשבר ב-45 ו-135 מעלות, שם ציר שלם ניצב לקו המבט.

### מנוע האיורים
`CabinetGlyph` מצייר כל ארגז ממפרט קצר לתוך מלבן. אותו קוד משרת את
האייקון הקטן בספרייה ואת ההדמיה על הקיר, כך שמה שנבחר הוא בדיוק מה
שנראה. כל איור מצהיר ב-`glyphList.ts` מה אפשר לכוונן בו, וטופס העריכה
מציג רק את זה.

## מודל הלוח

לוח הוא שני דברים שנקנים ומתומחרים יחד:

- **ליבה** — הגוף הפיזי: סנדוויץ׳ 17 מ״מ, MDF 9 או 18 (חום/ירוק/שחור),
  דיקט 5. לוח MDF יכול להגיע עם גוון אחר בצד השני; הוא נספר פעם אחת
  ומופיע בשורה השנייה כרזרבה, כי ספירה כפולה מבטיחה לוח שאינו קיים.
- **גוון** — מה שמודבק על הליבה. צבע ומרקם יחד קובעים אותו.

המחיר יושב בהצטלבות — `Finish.prices[materialId]` — וצירוף בלי מחיר פשוט
לא מוצע. כך אי אפשר לתמחר לבן על MDF במחיר של לבן על סנדוויץ׳.

הגוון של כל חלק נקרא בזמן אמת: מה שנקבע בארגז מנצח, ואחריו מה שנקבע
לפרויקט. ברירת המחדל אינה מועתקת לארגזים, ולכן שינוי בפרויקט חל מיד על
כל מי שלא נגעו בו.

**עובי הלוח אינו חלק מהגדרתו** — הוא משתנה בין משלוחים ונקבע מול הלוח
הפיזי. מה שבהגדרות הוא עובי נומינלי לחישוב בלבד.

## מידות שקובעות

`heightMm` הוא הגובה הכולל מהרצפה, כמו שמודדים בשטח. `socleMm` הן
הרגליים שבתוכו. ארגז תחתון סטנדרטי הוא **880 מ״מ כולל הרגליים** — זו
המידה שמזמינים לפיה: גובה עבודה 900, ומשטח בעובי 20 סוגר בדיוק.

תקרה או גב לא תמיד נבנים כלוח מלא. `rails` מסמן מה נבנה משתי רצועות של
10 ס״מ, ו-`backHeightMm` מקצר גב שאינו מכסה את כל הגוף. שניהם יורדים
מהפלטה ולכן גם מהמחיר, ומצוירים כרצועות — מי שרואה לוח מלא בציור יזמין
לוח מלא.

דלת, חלון ועמוד חוסמים הנחת ארגז. שקע ונקודת מים אינם חוסמים — הם
נקדחים בגב הארון.

## גיבוי, והספרייה שמגיעה עם האפליקציה

`src/db/backup.ts` הוא הדלת החוצה. הגיבוי הוא JSON קריא, והוא יוצא ונכנס
כטקסט ולא כהורדת קובץ — אפליקציה שנפתחה מקישור רצה לפעמים בתוך מסגרת
שחוסמת הורדות. מעתיקים, שולחים לעצמך, וזה הגיבוי.

שני גיבויים, כי הם עונים על שתי שאלות. **הכול** הוא מעבר למכשיר חדש,
ולכן השחזור מוחק ולא ממזג — מיזוג של שני מצבי עולם מייצר פרויקטים כפולים.
**הספרייה** היא הארגזים בלבד, בלי לקוחות, ואותה אפשר לשלוח למישהו אחר.

ייבוא ספרייה אינו נוגע בפרויקטים: ארגז שהונח על קיר שמר את מידותיו בעצמו
ברגע ההנחה, והוא אינו קורא מהספרייה.

`scripts/library-to-seed.mjs` ממיר ספרייה שיוצאה מהאפליקציה
ל-`src/catalog/shipped.ts`, ומרגע שהקובץ אינו ריק הוא זה שנזרע במקום
ארגזי התקן שב-`builtins.ts`. ככה ספרייה שנבנתה בנגרייה הופכת לספרייה שכל
מכשיר חדש מקבל. `--reset` מחזיר לארגזי התקן.

הזריעה קורית פעם אחת, לספרייה ריקה בלבד. מה שנמחק אינו חוזר ברענון, וגם
ספרייה שהוחלפה נשארת מוחלפת; "החזרת ארגזי התקן" ב"גיבוי והעברה" היא הדרך
היחידה חזרה, והיא מפורשת.

## כניסה ואבטחה

יש חשבון ברירת מחדל `admin` / `admin2026`. **זו נקודת פתיחה ולא הגנה:**
הסיסמה ידועה לכל מי שראה את הקוד או את כתובת האפליקציה, והנתונים יושבים
ב-IndexedDB ללא הצפנה. מסך הכניסה ומסך הצוות מסמנים אותה עד שהיא מוחלפת.

הנתונים עצמם אינם עוזבים את המכשיר — מי שפותח את האפליקציה החיה מקבל
בסיס נתונים ריק משלו, ולא את מה שיש אצלך.

## מוסכמות

- מידות במ״מ תמיד; סנטימטרים הם שפת תצוגה בלבד
